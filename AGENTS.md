# AGENTS.md

## Project overview

This repository is a standalone Angular 22 application demonstrating Angular Material with Firebase/Firestore.
The application uses zoneless change detection, lazy-loaded routes, SCSS, Tailwind CSS, ngx-translate, and Vitest.

## Setup and commands

- Use Node 24 (see `.nvmrc`) and Bun 1.3.14. Use Bun for dependency and script operations.
- Install dependencies with `bun install`.
- Start the development server with `bun run start`.
- Build the production application with `bun run build`.
- Run unit tests with `bun run test`.
- Run TypeScript, template, and style checks with `bun run lint`.
- Extract translation keys with `bun run i18n:extract`.

Run the narrowest relevant checks while developing. Before handing off code changes, run `bun run lint`,
`bun run test`, and `bun run build` when practical. If a check cannot run, state why.

## Angular conventions

- Follow the existing standalone component architecture; do not introduce NgModules for application features.
- Keep components on `ChangeDetectionStrategy.OnPush` and preserve zoneless compatibility.
- Prefer Angular's modern APIs and built-in template control flow. Use signals for new local reactive state when they
  fit, but stay consistent with existing RxJS pipelines and reactive forms when extending them.
- Use `inject()` for dependency injection, matching the existing code.
- Lazy-load route components and feature routes where possible.
- Generate Angular artifacts with the Angular CLI so the defaults in `angular.json` are applied.
- Keep selectors under the `app` prefix and follow the ESLint rules in `eslint.config.js`.
- Preserve strict typing. Do not use `any` to bypass type errors.

## Project structure

- Put application features under `src/app/<feature>`.
- Put reusable UI, services, guards, directives, DTOs, constants, and RxJS operators under `src/app/shared`.
- Keep component templates and SCSS beside their component TypeScript files.
- Use feature `index.ts` files only where the surrounding feature already follows that pattern.
- Define route names through `ROUTE_DEFINITION` rather than duplicating path strings.

## UI, styling, and accessibility

- Prefer Angular Material components and existing shared components before adding custom equivalents.
- Keep component styles scoped in their `.scss` files; reserve `src/styles.scss` for global styles.
- Follow the existing two-space formatting and the Prettier configuration.
- Ensure interactive controls are keyboard accessible, have an accessible name, and pass Angular template
  accessibility linting.

## Firebase and configuration

- Keep Firebase access behind AngularFire APIs and the existing provider/service boundaries.
- Never commit credentials, service-account keys, private configuration, or local emulator data.
- Do not weaken authentication guards or Firestore access assumptions merely to make UI flows pass.

## Internationalization

- User-facing text must use the existing ngx-translate mechanism.
- Keep `src/assets/i18n/en.json` and `src/assets/i18n/cs.json` synchronized when adding or changing keys.
- Preserve the existing namespaced and sorted translation-file format.

## Tests and generated files

- Add or update colocated `*.spec.ts` tests for behavior changes.
- Prefer observable user behavior and public APIs over testing implementation details.
- Do not edit generated build output under `dist/`, Angular cache files, or dependency contents.
- `src/app/version.ts` is generated by `bun run create-version`; regenerate it instead of editing it manually.

## Change discipline

- Keep changes focused and preserve unrelated work in the working tree.
- Do not change deployment workflows, Firebase targets, or dependency versions unless the task requires it.
- Use Angular-style conventional commit types configured in `.quick-commitlint.json`.
